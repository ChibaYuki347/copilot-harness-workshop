# ケーススタディ: チーム導入

約 3 か月かけて、12 人のプロダクトチームが TypeScript/Python のモノレポ全体で Copilot CLI を
導入した事例をもとにした合成ケースです。名称は変更していますが、導入の *流れ* 自体は
実際のものです。

## 出発点の状況

- **チーム:** エンジニア 12 人（バックエンド Python 8 人、フロントエンド TS 3 人、SRE 1 人）。
- **リポジトリ:** モノレポ 1 つ、約 25 万 LOC、複数サービス。
- **既存の AI 活用:** 場当たり的な Copilot の提案利用のみで、共有ルールはありません。
- **課題:** 各エンジニアが独自のコンテキスト付与プロンプトを書いていました。レビューでは、
  「AI らしい」アンチパターン（過剰な抽象化、未テスト、別の場所にある類似コードの複製）が
  ときどき見つかっていました。
- **目標:** AI 支援ワークフローを、12 個の個人ワークフローではなく、*チーム* の資産にすること。

## 選んだレイヤー

| レイヤー | 使う? | 理由 |
|---|---|---|
| カスタムインストラクション | ✅ | 必須のベースラインです。チームの標準スタイルを定義できます。 |
| パス別インストラクション | ✅ | フロントエンドとバックエンドでは求められる内容が異なります。 |
| プロンプトファイル | ✅ | 共有の `/new-service` と `/migration` のワークフローに使います。 |
| スキル | ✅ | レビューチェックリストを確実に回せる `pr-review` スキルです。 |
| フック | ✅ | 2 つあります。セッション終了時のシークレットスキャンと、編集時の整形です。 |
| MCP サーバー | ✅ | 組み込みの GitHub MCP と、非公開の「社内ドキュメント」MCP です。 |
| カスタムエージェント | ✅ | `security-reviewer` エージェントを 1 つ使います。 |

## 導入の進め方（順番どおり）

### 1 週目 — ベースラインの規約

2 人で `.github/copilot-instructions.md` の初版を約 3 時間で作成しました。難しかったのは
書くことではなく、規約を決めることでした。既存の `CONTRIBUTING.md` の内容は、
大部分をそのまま持ち込めました。

> **教訓:** AI 向けの規約ドキュメントは、書き残していなかった *チーム* の規約を表に出す
> きっかけになります。文書化の時間だけでなく、チームで話し合う時間も見込む必要があります。

### 2 週目 — パス別インストラクション

```
.github/instructions/
├── frontend.instructions.md   # applyTo: frontend/**
├── backend.instructions.md    # applyTo: backend/**
└── sre.instructions.md        # applyTo: ops/**, .github/workflows/**
```

各サブチームが自分たちのものを書き、PR レビューで承認しました。現在はコードと一緒に
バージョン管理されています。

### 3 週目 — PR レビュースキル

チームのレビューチェックリストを包み込む `pr-review` スキルです（[レシピ](../recipes/pr-review-skill.md) を参照）。
副次的な効果として、*人間* が見落としがちだったチェック項目（「CHANGELOG を更新したか」など）も
拾えるようになりました。

このスキルの `references/checklist.md` は、チームのレビュー基準における **唯一の正本** です。
バージョン管理でき、レビュー可能で、内容がずれていく Confluence ページではなくなりました。

### 2 か月目 — フック

2 つのフックを追加しました。

- **`sessionEnd` → シークレットスキャン。** [レシピ](../recipes/session-end-secret-scan.md) と同じです。
  警告のみで、実際の強制は引き続き CI が担います。
- **`postToolUse` → 自動整形。** edit/create ツールが書き込んだファイルに対して `pnpm prettier --write` または `ruff format` を実行します。差分を小さく保てます。

### 2 か月目 — 非公開 MCP サーバー

チームは、社内ドキュメント（Confluence 風）を検索ツールとして公開する小さな MCP サーバーを
構築しました。これによりエージェントは、「新しいサービスは普段どう構成しているか」といった問いに、
推測ではなくドキュメント検索で答えられます。

これは本格的な実装で、約 1 週間かかりました。チームがこれを作ったのは、*すでに*
ハーネスを整えており、何が足りないかを正確に見えていたからです。

### 3 か月目 — `security-reviewer` エージェント

PR レビュースキルの実行中に並列サブエージェントとして動くカスタムエージェントです（[examples/agents/security-reviewer.agent.md](https://github.com/ChibaYuki347/copilot-harness-workshop/blob/main/examples/agents/security-reviewer.agent.md) を参照）。
認証、シークレットの扱い、SQL / 文字列補間パターンを重点的に見ます。

以前は「誰かが思い出したときだけ」だった手動のセキュリティ確認が、今ではすべての PR
で実行されるようになりました。

## 結果（定性的）

- **オンボーディング:** 新しく入ったメンバーが、数週間ではなく数日で戦力化できます。規約が
  Wiki に埋もれているのではなく、*実行可能* な形になっているためです。
- **PR 品質:** 「これ、X で書き直せますか」という後工程のコメントが減りました。AI がすでに
  X をチーム標準として理解しているためです。
- **ずれの減少:** 規約が変わったら、チームは 1 本の PR でインストラクションファイルを更新します。
  次のセッションから全員に反映されます。
- **コスト:** 初期作業は 3 か月に分散したエンジニア約 1 人週分、その後の保守は月 1 時間程度です。

## 振り返り

- **1 週目より前にパス別インストラクションを作るのは早すぎます。** まずは単一の
  ベースラインから始め、摩擦が現実のものになってからパス別ファイルを切り出すべきです。
- **最初に MCP サーバーを作ってはいけません。** 「自分たちはこんなにすごい」と見せたくなる
  魅力的なプロジェクトですが、基本のハーネスを 1 か月使って初めて、*本当に* 欲しいツールが
  分かりました。
- **CI にもハーネスを固定します。** GitHub Action で `copilot -p '/pr-review'` を使い、
  各自のマシンだけでハーネスが動く状態を避けます。
- **定期的に削ります。** 3 か月後にはカスタムインストラクションが膨らみすぎていました。
  デフォルト動作になった項目や、別の場所に埋め込まれた項目は四半期ごとに見直して削除します。

## はまったアンチパターン

- **インストラクションを TODO リストとして使う。** 「X を追加するか考えよう」→ いいえ。
  インストラクションファイルは、*いま決まっていること* を書く場所であり、*将来あるかもしれないこと* を書く場所ではありません。
- **重複するスキル。** `pr-review` と `code-quality-check` が、最終的に 80% 同じことを
  していました。そこで統合しました。
- **やりすぎるフック。** 最初の `sessionEnd` フックは、シークレットスキャン、メトリクス集計、
  Slack 投稿まで行っていました。壊れやすくなったため、処理ごとに 1 つのフックへ分割しました。
