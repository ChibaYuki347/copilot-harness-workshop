# ケーススタディ

実在の人やチームが、実際にどのようにハーネスを組み立てているかをまとめたものです。各ケーススタディでは、
次の内容を扱います。

- **出発点の状況**（課題、制約、チーム構成）。
- 選んだ **レイヤー** とその **理由**。
- **導入の進め方** — 最初に何を入れ、次に何を追加し、三番目に何を行ったか。
- **結果** と **振り返り**。

## このセクションで扱う内容

- [**個人開発者**](solo-developer.md) — 1 人で複数のサイドプロジェクトを抱え、言語も混在するケース。
- [**チーム導入**](team-rollout.md) — 12 人のプロダクトチームがモノレポ全体で Copilot CLI を導入するケース。

## 持ち帰ってほしいポイント

これらの狙いは、そのまま真似することではありません。見るべきなのは **順番** です。どの
カスタマイズが最初に効き、次の一手をいつ追加し、何を後回しにしやすいかが分かります。

両方のケーススタディから得られる、実用的なヒューリスティックは次のとおりです。

> **まずはカスタムインストラクションから始め、スキルを 1 つ追加します。そのうえで、
> フックや MCP が本当に必要かを判断します — 多くの場合、この段階ではまだ不要です。**

ハーネスの大半は、規模が大きくなったとき（チーム調整や自動化）に効いてきます。1 つの
リポジトリを扱う個人開発者であれば、3 つのテキストファイルで価値の 80% を得られます。
